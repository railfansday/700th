#10207. Debouncing: The Tiny Hardware Problem That Haunts Every Click, Keypress and Button

📅 25 Oct 2026 | Category: other | Source

Every physical button you have ever pressed lies a little. When metal contacts inside a switch close, they do not make one clean connection. They bounce, rapidly touching and separating for a few milliseconds before settling. To a fast enough circuit, one press looks like several. This phenomenon, called contact bounce, is why engineers write debounce logic, and why your old mouse may suddenly start double-clicking on its own.

What bounce looks like

If you put an oscilloscope on a mechanical switch, a single press shows a jagged burst of on/off transitions lasting anywhere from under 1 ms to over 10 ms, depending on the switch, its age and its condition. Release often bounces too.

A microcontroller sampling every few microseconds would happily report five presses where a human made one.

Debouncing strategies

Engineers handle this in hardware, software or both.

Hardware debouncing

  • RC filter + Schmitt trigger: A resistorâ€“capacitor network smooths the signal, and a Schmitt trigger converts it back into a clean edge.
  • SR latch with an SPDT switch: A setâ€“reset latch locks the first contact, making later bounce irrelevant.

These approaches are robust but add components and cost.

Software debouncing

Most modern devices debounce in firmware. Common approaches:

1. Delay after the first edge (eager):

if (pin_changed && (now - last_change) > DEBOUNCE_MS) {
    report_event();
    last_change = now;
}

This is fast to respond, but noise can trigger it.

2. Wait for a stable state (deferred):

if (raw != stable) {
    if (++count >= STABLE_SAMPLES) { stable = raw; report_event(); count = 0; }
} else {
    count = 0;
}

This is more reliable, but it adds latency equal to the stability window.

3. Integrator or shift-register methods: Shift samples into a byte and treat 0xFF as pressed and 0x00 as released. It is elegant and cheap.

The latency trade-off

Here is the catch: debounce time is latency. Gaming mouse makers compete on responsiveness, so firmware may use very short debounce windows. That works fine when switches are new and clean. As contacts wear or oxidise, bounce lasts longer, can exceed the debounce window and gets reported as a second click.

That is the root of the famous "mouse double-click problem". It is not usually a software bug, but an ageing switch outliving its firmware assumptions.

Some manufacturers now let users adjust debounce time in companion software, trading a few milliseconds of latency for reliability. Others moved to optical switches, where a light beam replaces metal contacts and bounce largely disappears.

Observing bounce without an oscilloscope

You can see the symptoms from the operating system side. Browsers expose mousedown/mouseup events with high-resolution timestamps via event.timeStamp. If you log the interval between consecutive presses of the same button, human-made presses rarely come closer than about 50â€“80 ms. Intervals of a few milliseconds suggest bounce leaking through.

A minimal logger:

let last = 0;
addEventListener("mousedown", (e) => {
  const t = e.timeStamp;
  console.log(e.button, (t - last).toFixed(1), "ms");
  last = t;
});

For non-developers, a ready-made double click test does the same thing with a friendlier interface. You press a button 25 times, and it logs each interval, flags unusually short repeats and exports a CSV. It is a useful diagnostic, with the caveat that it measures what the browser observes, after OS and firmware processing, and not the raw electrical signal.

Beyond mice

Bounce affects anything with mechanical contacts:

  • Keyboards: Chattering keys type double letters. Mechanical keyboard firmware such as QMK exposes debounce algorithms and timing.
  • Embedded projects: Every Arduino beginner meets bounce on their first button.
  • Industrial controls: Limit switches and relays need debouncing to avoid false triggers.
  • Rotary encoders: Bounce causes skipped or reversed steps, a classic cause of jumpy scroll wheels.

Takeaways

  1. Physical switches always bounce. The only question is by how much.
  2. Debounce logic trades latency for reliability.
  3. Ageing switches can outgrow their firmware's debounce window.
  4. Optical switches and adjustable debounce are the modern answers.
  5. You can observe the symptoms in a browser in a few lines of JavaScript.

Next time your mouse opens a folder you only meant to select, you will know exactly what is going on: a few microscopic metal contacts, bouncing just a little too long.

#10208. Python rate limiting in 2026: drogue vs slowapi vs limits vs flask-limiter

📅 25 Oct 2026 | Category: other | Source

You're adding rate limiting to a Python web app. The usual suspects are slowapi, flask-limiter, django-ratelimit, and the limits library. There's also drogue. Here's how they compare.

The short version

drogue slowapi flask-limiter limits
request: Request in signatures No Yes Yes N/A (standalone)
FastAPI Yes Yes No Via adapter
Django Yes No No Via adapter
Flask Yes No Yes Via adapter
Algorithms 5 (Token Bucket, Sliding, Fixed, GCRA, Leaky) 1 (Fixed Window) 1 (Fixed Window) 3
WebSocket Yes No No No
DDoS detection Yes No No No
Auto-ban Yes No No No
CAPTCHA challenges Yes No No No
Shadow mode Yes No No No
Custom 429 body error_renderer Custom handler Custom handler N/A
Zero runtime deps Yes No (starlette) No (flask) No

The request: Request problem

This is the biggest difference and the reason drogue exists.

slowapi requires you to add request: Request to every decorated endpoint:

# slowapi
from slowapi import Limiter
from slowapi.util import get_remote_address
from starlette.requests import Request

limiter = Limiter(key_func=get_remote_address)

@app.get("/api/data")
@limiter.limit("10/minute")
async def get_data(request: Request):   # rate limiter leaked into your signature
    return {"data": "value"}

Now your business logic is coupled to the rate limiter. Change the limiter,
rewrite every endpoint. Test the endpoint without HTTP, mock the request.

drogue extracts identity from the ASGI context without touching your signature:

# drogue
from drogue.adapters.fastapi import DrogueLimiter

limiter = DrogueLimiter(app)

@app.get("/api/data")
@limiter.limit("10/minute")
async def get_data():                   # clean
    return {"data": "value"}

Algorithm choice matters

slowapi uses Fixed Window only. "30/minute" means exactly 30 requests,
then hard stop. That's fine for strict quotas but harsh on bursty traffic.

drogue defaults to Token Bucket, which allows short bursts above the average
rate. A "30/minute" limit with Token Bucket might briefly allow 35 requests,
then smooth out. For strict quotas, use algorithm=AlgorithmType.FIXED_WINDOW.

The choice between burst-friendly and strict-per-window is a design decision,
not a bug. slowapi just doesn't offer the option.

WebSocket rate limiting

Neither slowapi nor flask-limiter supports WebSocket rate limiting. If you
have real-time features (chat, notifications, games), you need drogue or
roll your own.

Built-in defense layers

drogue goes beyond rate limiting:

  • DDoS detection - Z-score anomaly detection across client rate distributions
  • Auto-ban - progressive ban with doubling duration (5m to 160m)
  • Trust scoring - 9x throughput for verified users (state machine: Unknown/Normal/Trusted/Distrusted/Banned)
  • CAPTCHA challenges - Turnstile integration with signed pass cookies and replay-proof tokens
  • Circuit breaker - Closed/Open/HalfOpen states for failing backends
  • Shadow mode - test rules without enforcing, collect metrics first

All off by default. Enable what you need.

Custom 429 responses

slowapi makes you replace the exception handler entirely. drogue gives you
a callback:

from starlette.responses import JSONResponse

def my_renderer(request, exc, headers):
    return JSONResponse(
        {"error": "rate_limited", "retry_after": exc.retry_after},
        status_code=429,
        headers=headers,
    )

limiter = DrogueLimiter(app, error_renderer=my_renderer)

Rate limit headers (X-RateLimit-Limit, X-RateLimit-Remaining, Retry-After)
are injected automatically.

When to use which

Use drogue if you want clean signatures, multiple algorithms, WebSocket
support, defense layers, or you're migrating from slowapi and want less code.

Use slowapi if you're on FastAPI only, already have it integrated, and
don't mind request: Request in your signatures.

Use flask-limiter if you're on Flask and want something battle-tested.

Use limits if you need a standalone rate limiter (CLI tools, scripts, etc.)
without a web framework.

Install 

pip install drogue[fastapi]   # or [django], [flask], [drf]

#10209. Understanding SQEs and CQEs with kqring on FreeBSD

📅 25 Oct 2026 | Category: other | Source

If you have used an event loop, you have probably written some variation of this:

  1. Wait for a socket to become readable.
  2. Read from it.
  3. Process the bytes.
  4. Go back to waiting.

A completion-based I/O interface moves some of that work across the application/kernel boundary. Instead of asking which sockets might be ready, the application can describe the reads it wants and collect their results later.

kqring is an experimental FreeBSD kernel module that exposes an io_uring-oriented interface using FreeBSD's own kernel facilities. It is a useful example for understanding what submission and completion queues actually do, and why their memory-lifetime rules matter.

Readiness and completion answer different questions

For a network receive, a readiness notification answers:

Can this socket probably be read without waiting?

The application still needs to perform the receive. Another thread might consume the available data first, so the application also needs to handle readiness changing before it acts.

A receive completion answers:

What happened to the receive that was submitted?

That result might be 100 bytes read, an error, or end of file. The operation itself has been attempted or completed according to the interface's contract.

This distinction describes the network paths, not everything kqueue can do. FreeBSD's kqueue also supports other event sources, including asynchronous I/O completion notifications.

An SQE describes work

SQE stands for Submission Queue Entry. It contains the operation and its arguments.

Conceptually, a read request might look like this:

operation: READ
file:      descriptor 7
buffer:    address of a 4096-byte buffer
length:    4096
user_data: 42

A real program also has to set up the ring, publish the entry with the right memory ordering, and tell the kernel about it. A library such as liburing handles that bookkeeping; the real code is below.

The user_data value belongs to the application. It could be an integer identifying a request or a value associated with application state. The kernel returns it with the result so the application can match the completion to the right request.

A CQE reports a result

CQE stands for Completion Queue Entry. Its important fields are:

Field Meaning
user_data The value associated with the submitted request
res The operation's result, such as bytes transferred or a negative error
flags Additional information about the completion

If the example read transfers 100 bytes, a completion could contain:

user_data: 42
res:       100
flags:     0

An error is reported through a negative result. A read that reaches end of file normally reports zero bytes.

The basic exchange is:

Application prepares SQEs
          |
          v
Kernel consumes requests and performs or schedules work
          |
          v
Kernel posts CQEs
          |
          v
Application collects results and updates its own state

Completions need not arrive in submission order. Matching by user_data lets the application manage requests that finish at different times.

The same read in C

Here is that read with liburing, built against kqring's liburing 2.9 port and saved as readone.c. Error handling is trimmed to the essentials:

#include <liburing.h>
#include <fcntl.h>
#include <stdio.h>
#include <string.h>
#include <unistd.h>

int
main(void)
{
    struct io_uring ring;
    struct io_uring_sqe *sqe;
    struct io_uring_cqe *cqe;
    char buf[4096];
    int fd, ret;

    ret = io_uring_queue_init(8, &ring, 0);
    if (ret < 0) {
        fprintf(stderr, "queue_init: %s\n", strerror(-ret));
        return (1);
    }
    fd = open("/etc/hosts", O_RDONLY);
    if (fd < 0) {
        perror("open");
        return (1);
    }

    /* Describe the read: an SQE. */
    sqe = io_uring_get_sqe(&ring);
    io_uring_prep_read(sqe, fd, buf, sizeof(buf), 0);
    io_uring_sqe_set_data64(sqe, 42);
    io_uring_submit(&ring);

    /* Collect its result: a CQE. */
    ret = io_uring_wait_cqe(&ring, &cqe);
    if (ret < 0) {
        fprintf(stderr, "wait_cqe: %s\n", strerror(-ret));
        return (1);
    }
    printf("user_data=%llu res=%d\n",
        (unsigned long long)io_uring_cqe_get_data64(cqe), cqe->res);
    io_uring_cqe_seen(&ring, cqe);

    close(fd);
    io_uring_queue_exit(&ring);
    return (0);
}

From the repository's liburing directory, after make and with kqring.ko loaded:

cc -O2 -I work/liburing-liburing-2.9/src/include -I freebsd/include \
    -include freebsd/include/config-host.h -o readone readone.c work/out/liburing.a
./readone

On a FreeBSD 15.1 machine whose /etc/hosts is 1,035 bytes, it prints:

user_data=42 res=1035

The source is the same as it would be on Linux. What differs is underneath: liburing's three system calls go to kqring's, and values such as O_RDONLY and the error numbers in res are FreeBSD's.

One request can produce several completions

A multishot request can remain active after producing a result. For example, a multishot receive can produce completions for successive receives without requiring the application to submit an entirely new receive request each time.

IORING_CQE_F_MORE tells the application that the request remains active and can produce more completions. A completion without that flag ends the multishot request.

This changes the application's bookkeeping. It must not discard the request state just because the first CQE arrived. It also needs a buffer strategy appropriate for multiple results, such as provided buffers, and must handle the conditions that terminate the request.

The kernel still needs somewhere to execute the work

A ring is a communication mechanism. It does not make every operation cheap or automatically nonblocking.

kqring uses several execution paths:

  • Ready socket operations can execute during the submitter's entry into the kernel.
  • Sockets that would block wait for a socket callback that queues a retry.
  • Eligible cached file reads and ready pipes can execute inline.
  • Operations that need to wait can run on kernel workers associated with the owning process.
  • Supported disk-device operations can use the native bio path.

The code also uses kqueue internally. Its non-socket polling adapter, called kpoll, registers events for objects such as pipes and eventfds and converts them into completions.

So kpoll and kqueue are not competing choices here. Kpoll is the part of kqring that connects internal kqueue events to the submission/completion model.

Batching can save work

Suppose many sockets already have data available. A readiness loop can collect their events together, but the application still performs the receives. A completion interface can describe those receives in advance and collect their results as a batch.

The benefit depends on the workload. Preparing queue entries, holding references, scheduling workers, and posting results all have costs. One operation per kernel entry may add overhead without enough batching or overlap to recover it.

That is why an evaluation needs more than the fastest benchmark row. Useful questions include:

  • How many operations are submitted together?
  • Is the data already available, or does the request need to wait?
  • Does execution require a worker handoff?
  • How much CPU time and memory does the workload consume?
  • Which event marks the operation as finished for the measurement?

An interface can make one workload cheaper and another more expensive. The project documents both favorable and unfavorable microbenchmark results; they should not be read as a claim that every application becomes faster.

A completion also has an ownership meaning

The buffer address in a request is more than an argument. It is a promise that the memory remains usable for as long as the operation needs it.

Copying the request's metadata does not copy the payload. Once submission has consumed an iovec description, for example, its metadata may be reusable under the interface contract while the described data buffer still has to remain available.

Cancellation adds another distinction. In kqring, a successful asynchronous cancellation result can arrive before the target worker has returned. The target's final completion is the event to wait for before reusing its ordinary I/O buffer. Requesting interruption is not the same as proving the worker has stopped.

Zero-copy sends have a further boundary. The primary send result can arrive while outgoing network buffers still retain references to the application's pages. A later release notification tells the application when it may reuse that transmission memory. Neither notification means that the remote application has processed the data.

For each request, ask: which completion actually ends the resource's lifetime obligation?

Compatibility has limits

kqring follows io_uring structures and operation identifiers, but uses native FreeBSD values for flags such as O_* and MSG_*, and native error numbers in completion results.

Its public header supplies three entry points:

Linux interface Native kqring wrapper
io_uring_setup() kqring_setup()
io_uring_enter() kqring_enter()
io_uring_register() kqring_register()

The repository includes an overlay for liburing 2.9. This can preserve the library-level programming model, but Linux-specific assumptions in an application still need review. This is a native source-porting interface, not a way to execute an unchanged Linux binary.

There are behavioral differences too. Rings belong to one process, and a forked child cannot generally submit work through its parent's ring. Signal-mask handling and exec behavior also differ. A familiar operation name does not remove the need to read those contracts.

Where the implementation stands

The current project documentation identifies FreeBSD 15.1-RELEASE, amd64, with a GENERIC kernel and matching kernel sources as the supported system. Other releases and architectures have not been tested according to that documentation.

The module is an experimental preview and has not had an independent security audit. Functional tests and compatibility tests help check specific behaviors; they do not establish the absence of kernel concurrency or memory-safety bugs.

The source repository contains the implementation, architecture notes, compatibility differences, tests, and benchmark procedure. For the version discussed here, see the project overview at release 0.1.0.

The useful mental model is a request with an explicit lifetime: the SQE describes it, the kernel chooses how it executes, and CQEs report the state transitions the application needs to observe. Understanding those transitions is what makes the interface usable safely.

#10210. I Built a Calorie Tracker for Beginners — Here's What Simplicity Taught Me

📅 25 Oct 2026 | Category: other | Source

Most calorie tracking apps fail beginners in the first week. Not because people lack discipline, but because the apps ask for too much: weigh every gram, search through endless food databases, and decode charts before you have even finished your first day.

I built CalyFit around the opposite idea: the simplest calorie tracking for busy people and beginners. Here is what building it taught me.

1. Every extra tap loses a user

The first version of my food log had portion sizes, cooking methods, and half a dozen optional fields. Testers skipped logging entirely. When I cut logging down to the essentials — pick the food, confirm the portion, done — people actually kept going.

Lesson: for beginners, a good-enough entry today beats a perfect entry never made.

2. Barcode beats typing

Typing "chicken sandwich" into a search box and picking from fifty near-identical results is friction. Scanning a barcode and getting the item instantly is not. That one interaction changed how often people logged. If you are building any kind of tracker, find the one input your users repeat daily and make it nearly free.

3. Habits beat perfection

Nobody eats perfectly, and an app that makes you feel guilty about it gets deleted. CalyFit tracks the basics that keep people going: calories and macros, daily steps, water and sleep, plus BMI and personalized goals. A short daily streak of "I logged today" does more for a beginner than any advanced analytics dashboard.

4. Build in public with zero budget

CalyFit was built and marketed with a $0 budget. It is rated 4.3 stars on Google Play, and every bit of growth so far came from consistent, honest content rather than ads. Building in public forced me to be honest about what the app does and does not do — and users trust that more than polished marketing.

What I would do differently

I would have talked to beginners before writing a single line of code. I assumed people wanted more features. They wanted fewer, clearer ones. If you are building your first app, find five people in your target audience and watch them use a rough version. Their confusion is your roadmap.

The takeaway

Simplicity is not a lack of features. It is a decision about which friction to remove first. For a beginner, the best tracking app is the one they still open in week three.

#10211. Ilang pizza? For every meetup volunteer who says “kalahati lang naman ang pupunta”

📅 25 Oct 2026 | Category: other | Source

This is a submission for the Hacktoberfest Open-Source AI Challenge Week 3: Slow and Steady

What I Built

It's Friday night. Tomorrow is a PyWorks workshop, {{RSVPS_EXAMPLE}} people have RSVP'd, and the volunteer group chat has exactly one question:

"Ilang pizza?" (How many pizzas?)

I volunteer with Python Philippines (PythonPH), an all-volunteer community: 3,394 members on Meetup, 77 past events listed. We run weekday-evening PyMeets talks at offices in BGC and Makati, Saturday PyWorks workshops (like PyWorks October 2026: Data and AI at UP-Ayala TechnoHub), the online WFH Pythonista, and PyKids.

Our events are free, which means no-shows. The night before, someone has to guess:

  • how many pizza boxes to order
  • how many waitlisted people to let in
  • how many chairs, name tags and e-certificates to prepare
  • what headcount to give the building admin, because BGC and Makati offices want a guest list

The house rule is "kalahati lang naman ang pupunta": about half will show. Guess high and we pay for cold leftover Hawaiian. Sayang. Guess low and the last person in gets a sad crust, or isn't on the lobby's guest list.

Ilang pizza? does that guessing for the tired volunteer. Feed it past RSVP and check-in exports (Meetup, Luma, ti.to or Google Forms). TabPFN predicts who shows up, plain Python turns that into pizza, waitlist, seat and e-cert numbers, and a local Gemma drafts the emails in Taglish or English.

For those {{RSVPS_EXAMPLE}} RSVPs, it says {{PREDICTED_RANGE}} people will show. The plan: order for that, send the drafts, go to sleep.

The patron saint here is Juan Tamad, the Filipino folk character who lay under a guava tree waiting for the fruit to fall into his mouth. For International Sloth Day, that's the design goal: the volunteer lies down and the answer falls out. 🦥

Code

Jericho0912 / ilang-pizza

Built with PriorLabs-TabPFN · Gemma 4 via Ollama · runs on the organizer's laptop

Ilang pizza? is Tagalog for "How many pizzas?", the question someone always asks the night before a meetup. It was built for Python Philippines (PythonPH) and works for any community that runs free events.

The problem

As of October 2026, PythonPH's Meetup group has 3,394 members and lists 77 past events: PyMeets talks on weekday evenings at office venues in BGC and Makati PyWorks workshops on Saturdays, WFH Pythonista online, and PyKids. The events are free, which is great until the night before:

  • RSVPs aren't turnout. A free "Going" costs nothing to give, so some of them never come.
  • Pizza for no one. Order for every…
View on GitHub

How I Built It

The rule I set: open models do what they're good at, plain Python does the arithmetic, and nothing personal leaves the laptop.

Pipeline: exports → features → TabPFN → headcount distribution → plan → Gemma → CLI and Gradio UI

TabPFN: who's actually coming?

TabPFN is Prior Labs' tabular foundation model, and it suits community data suspiciously well: no training loop, no hyperparameter tuning, strong on small tables of a few thousand rows, and fine with missing values.

Each RSVP becomes a row of 27 features, using only what was known beforehand:

  • RSVP timing: days ahead, place in the sign-up order, guests
  • Attendee history: regular or first-timer, from strictly earlier events
  • Event: series, weekday evening vs Saturday, online vs in-person, waitlist, food
  • PH calendar: holidays, long weekends, the wet season, and payday. Pay lands on the 15th and month-end (kinsenas at katapusan), and the broke days before are petsa de peligro. A free talk still costs fare and dinner.
  • Rain: daily rain at the venue, or your own PAGASA table. Weather data by Open-Meteo.com.

The default checkpoint is TabPFN v2's open weights (Prior Labs License: Apache 2.0 plus attribution). TabPFN-3.5 is opt-in: its license is non-commercial and non-production, so an organizer who wants it reads and accepts that license themselves, then sets TABPFN_TOKEN.

From probabilities to a headcount

TabPFN rates the regular who never misses PyMeets high and the first-timer who RSVP'd three weeks ago low. Summing gives an average, but a pizza order needs the risk too.

So each RSVP is a weighted coin flip with its own odds (weighted, because "+1 guest" is two heads). If the coins were independent, the total would follow a Poisson-binomial distribution, computed exactly rather than simulated. But a downpour or a jammed EDSA moves everyone at once, so the distribution is mixed over a shared event-day shock, sized by how far earlier forecasts missed. That gives the odds of every headcount, and a p10 to p90 range as wide as our history says it should be.

Decisions: plain Python, simple math

The LLM never does math. The planner does, with adjustable defaults:

  • Pizza: order for the 75th percentile of heads, not every RSVP. Boxes = ⌈heads × 3 slices ÷ 8 per box⌉, so a p75 of 40 heads means 15 boxes. Add a box price to see pesos saved.
  • Waitlist: fold waitlisted RSVPs (with their own odds) into the distribution and release as many as keep P(heads > capacity) ≤ 10%.
  • Seats, name tags, e-certificates: the 90th percentile, counting the people just let in.

Why p75 for pizza but p90 for chairs? Leftover pizza costs money. A missing chair costs dignity.

Gemma: the emails, locally

Gemma 4 E4B runs through Ollama (gemma4:e4b) on the 16 GB Apple M5 Mac I built this on. TabPFN and Gemma together caused memory pressure, so they take turns. Gemma drafts four emails in Taglish (Tagalog plus English, how we talk) or English: reconfirm, waitlist release, catering order and venue headcount. It also explains the forecast in plain words.

Gemma only sees aggregates: the forecast summary, the plan, and event title, date and venue. Every prompt passes a privacy guard that rejects emails, PH mobile numbers and attendee hashes. Ilang pizza? predicts the crowd, not the person.

Ask Juan

Juan is a tiny agent for lazy questions:

  • "Ilang pizza para sa next PyMeets?" (How many pizzas for the next PyMeets?)
  • "Ilan pa pwede i-release sa waitlist kung 80 lang ang venue?" (How many more can we let in from the waitlist if the venue only fits 80?)

Gemma picks a tool (forecast, plan, draft…) and its arguments as JSON, Python runs it, and Gemma phrases the answer. Each reply lists its tool calls, so you can check Juan's work.

Why the LLM never does the math: during the build, Gemma once filled in "1 slice per box" on its own and answered "19 boxes". Now Juan only uses a number the organizer actually typed, and a draft with an invented number (or no Ollama at all) falls back to a hand-written template. Juan is lazy, not sloppy.

What I learned: I'd planned on Ollama structured outputs (the server enforces a JSON schema), but on my Mac its MLX runner said "structured output is unavailable" for gemma4:e4b. So the client puts the schema in the prompt and parses the reply leniently; about 30 real calls, all parsed. Thinking mode is off by default: about 3.5x faster, no visible quality loss.

#10212. BiCS FLASH memory controller error correction and data reliability enhancement (ECC) function

📅 25 Oct 2026 | Category: other | Source

High-capacity, high-density flash memory such as BiCS FLASH (3D NAND) is prone to bit inversion due to minute charge loss (retention degradation) and interference between adjacent cells (read disturb), making robust error correction (ECC: Error Correction Code) essential. While this is usually handled by hardware (LDPC or BCH engine), we have created sample code here that simulates a process where the device driver (software layer) controls and monitors the hardware ECC engine, and performs read retries (re-reading by adjusting the read voltage) as needed.

This code complies with the Ministry of Economy, Trade and Industry's IPA's "ESCR [C language version] Ver. 3.0," and thoroughly implements defensive programming, constant definition, and const qualifiers.

1. Sample Code 

#include <stdint.h>
#include <stdbool.h>
#include <stddef.h>

/* Constants Definition (Elimination of Magic Numbers) */
#define BICS_PAGE_DATA_SIZE         (4096U) /* User data size (4KB) */
#define BICS_PAGE_PARITY_SIZE       (256U)  /* Parity data size */
#define BICS_MAX_CORRECTABLE_BITS   (120U)  /* Maximum correctable bits (Assuming LDPC) */
#define BICS_MAX_READ_RETRY_COUNT   (5U)    /* Maximum limit for read retry (voltage shift) */

/* ECC Operation Result Codes */
typedef enum {
    BICS_ECC_SUCCESS = 0,         /* No errors (or parity generation successful) */
    BICS_ECC_CORRECTED = 1,       /* Errors successfully corrected */
    BICS_ECC_UNCORRECTABLE = 2,   /* Uncorrectable errors (e.g., retry limit exceeded) */
    BICS_ECC_INVALID_PARAM = 3    /* Invalid parameters provided */
} bics_ecc_result_t;

/* Mock Interface for Hardware ECC Engine */
typedef struct {
    /* Reads data/parity and returns the number of error bits using Hard Decision */
    uint32_t (*hw_decode_hard)(const uint8_t* data, const uint8_t* parity);
    /* Shifts the read reference voltage (Vth) for Read Retry */
    bool (*hw_shift_read_voltage)(uint8_t retry_step);
    /* Reads the raw page data from NAND flash again */
    bool (*hw_read_page_raw)(uint32_t block, uint32_t page, uint8_t* data, uint8_t* parity);
} bics_ecc_hw_engine_t;

/* ECC Management Context */
typedef struct {
    bics_ecc_hw_engine_t hw_engine;
} bics_ecc_context_t;

/**
 * @brief  Generates parity data during a write operation (Encoding)
 * @note   ESCR Compliant: NULL pointer checks, const correctness applied
 */
bics_ecc_result_t bics_ecc_encode(
    const bics_ecc_context_t* const ctx,
    const uint8_t* const data,
    uint8_t* const parity_out) 
{
    if ((ctx == NULL) || (data == NULL) || (parity_out == NULL)) {
        return BICS_ECC_INVALID_PARAM;
    }

    /* In a real scenario, this transfers data to the hardware to generate parity. */
    /* For simulation purposes, we initialize the parity buffer to 0. */
    for (uint32_t i = 0U; i < BICS_PAGE_PARITY_SIZE; i++) {
        parity_out[i] = 0x00U;
    }

    return BICS_ECC_SUCCESS;
}

/**
 * @brief  Performs error correction (Decoding) and Read Retry on read operations
 * @note   ESCR Compliant: Comprehensive error handling, clear loop boundaries
 */
bics_ecc_result_t bics_ecc_decode_with_retry(
    const bics_ecc_context_t* const ctx,
    uint32_t block,
    uint32_t page,
    uint8_t* const data,
    uint8_t* const parity) 
{
    if ((ctx == NULL) || (data == NULL) || (parity == NULL)) {
        return BICS_ECC_INVALID_PARAM;
    }
    if ((ctx->hw_engine.hw_decode_hard == NULL) || 
        (ctx->hw_engine.hw_shift_read_voltage == NULL) || 
        (ctx->hw_engine.hw_read_page_raw == NULL)) {
        return BICS_ECC_INVALID_PARAM;
    }

    uint8_t retry_count = 0U;
    uint32_t error_bits = 0U;

    while (retry_count <= BICS_MAX_READ_RETRY_COUNT) {
        /* Execute error detection and correction via Hardware ECC Engine */
        error_bits = ctx->hw_engine.hw_decode_hard(data, parity);

        if (error_bits == 0U) {
            return BICS_ECC_SUCCESS; /* No errors found */
        }
        if (error_bits <= BICS_MAX_CORRECTABLE_BITS) {
            return BICS_ECC_CORRECTED; /* Errors were correctable */
        }

        /* If uncorrectable, perform a Read Retry by adjusting the read voltage */
        retry_count++;
        if (retry_count <= BICS_MAX_READ_RETRY_COUNT) {
            if (!ctx->hw_engine.hw_shift_read_voltage(retry_count)) {
                return BICS_ECC_UNCORRECTABLE; /* Voltage shift operation failed */
            }
            if (!ctx->hw_engine.hw_read_page_raw(block, page, data, parity)) {
                return BICS_ECC_UNCORRECTABLE; /* Raw read operation failed */
            }
        }
    }

    /* Uncorrectable ECC error (UECC) occurs if correction fails after maximum retries */
    return BICS_ECC_UNCORRECTABLE;
}

Key Points of ESCR Ver.3.0 Compliance

  1. Ensuring NULL Safety (M101 / M102, etc.): Strict NULL checks for structure pointers and hardware operation function pointers are performed at the beginning of functions in bics_ecc_encode and bics_ecc_decode_with_retry.

  2. Strict Const Modifier Use (M113): The const modifier is applied to argument pointers that cannot be changed (context, read-only data). This prevents unexpected data corruption (such as buffer overflows) at the compilation stage.

  3. Elimination of Magic Numbers (M122): Page size, maximum number of retries, and allowable error bits are all defined using #define (or enum), and constants are given the U suffix to indicate they are unsigned.

  4. Use of fixed-length integer types (M203): Instead of using environment-dependent types such as int, we have standardized to uint32_t and uint8_t from , eliminating embedded-specific data size issues.
