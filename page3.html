#34851. Vercel Drives is now generally available

📅 27 Oct 2026 | Category: other | Source

Vercel Drives is now generally available for Vercel Sandbox on Hobby, Pro, and Enterprise.

A Drive is persistent storage that you mount as a directory in a Vercel Sandbox. Its files remain available after the sandbox stops, so later runs and other sandboxes can access them by mounting the same Drive.

Use Drives to preserve an agent’s workspace or file-based memory across runs, or to make datasets, models, dependencies, and build artifacts available across sandboxes.

You can also fork a Drive into independent writable Drives. Forks inherit the source Drive's data, region, and maximum size, then store their own changes. Parallel workers can start with the same files and make changes without affecting the original or one another.

#34849. Vercel Connect now supports Secure Compute

📅 27 Oct 2026 | Category: other | Source

Vercel Connect now supports Secure Compute, allowing connectors to reach providers with IP allowlists, such as Salesforce and Snowflake.

With Secure Compute routing enabled, Connect’s provider requests use the selected network’s dedicated static IP addresses instead of Connect’s shared IPs. Requests to obtain and refresh access tokens follow that route; your app’s direct API routing is unchanged by this setting. Credential management stays the same, so you don’t need to store long-lived provider secrets in your app or build OAuth flows yourself.

To enable Secure Compute routing for a supported connector and all projects that use it:

  • Open your connector’s Settings in the Vercel dashboard.

  • Under Secure Compute Routing, choose an existing network.

  • If your provider uses an IP allowlist, add the selected network’s displayed IP addresses to it in the provider’s settings.

  • Save your changes in Connect.

Requests for initial connector creation and all provider discovery requests bypass the selected network and connect directly to providers. If the selected network is unavailable, routed requests fail instead of falling back to Connect’s shared IPs.

Read the Secure Compute routing documentation for configuration details.

#34844. Python on Vercel is now generally available

📅 27 Oct 2026 | Category: other | Source

Python on Vercel is now generally available. Build and run Python applications with the frameworks, libraries, and tools you already use.

Vercel automatically detects supported frameworks and configures the build and deployment. Your applications run on Fluid compute, which manages concurrent requests and scales with traffic. Idiomatic Python SDKs let you work with storage, queues, durable workflows, and AI models directly from Python. For full-stack projects, the Python backend and frontend share a workflow for local development, preview deployments, and production releases.

Our goals for Python on Vercel

Ten months ago, we set out to make Vercel the best place to build and run Python applications. We wanted the experience to fit how Python developers already work, with three goals guiding our decisions:

  • Idiomatic Python SDKs. Working with Vercel infrastructure should feel familiar to Python developers, with APIs that use type annotations, async/await, and context managers.

  • A shared workflow for both the frontend and backend. Python applications often include a JavaScript frontend, so developers should be able to run both locally, review them in the same preview deployment, and release or roll them back together.

  • Compatibility with the Python ecosystem. The runtime should use CPython, the standard Python interpreter, on Linux to preserve compatibility with the packages and tools Python developers already rely on.

The first test of those goals is what happens when you deploy a Python application on Vercel: its framework, dependencies, and project structure should guide how it’s built and run.

Deploying Python applications on Vercel

We’ve worked to make Python feel native on Vercel. Vercel reads your project’s dependency files, including those managed by uv, and automatically detects frameworks such as FastAPI, Flask, Django, and FastHTML. Framework defined infrastructure configures builds and request routing, with framework-specific support for serving static assets through the CDN.

For applications with a frontend, Vercel Services brings both parts into one project. Running vercel dev starts them together, and shared previews let you test backend changes with the frontend that uses them.

For long-running workers that pull jobs from queues or databases, Vercel Daemons keeps your containers running with your Python code along with any of its packages, and system dependencies.

Python SDKs for Vercel infrastructure

A Python backend might need to store files, send messages, run durable workflows, or call AI models. We’ve built Python SDKs for these tasks, with APIs that follow the conventions of the language:

These SDKs work alongside your framework and libraries, and the example below shows how they connect within a full-stack application.

Start building with Python on Vercel

Whether you’re starting a new project or deploying existing code, the framework guides cover setup and deployment on Vercel. For a guided full-stack project, the Python on Vercel course walks through building a FastAPI backend and Next.js frontend, then deploying them together with Services.

To show how these pieces work together, I built a collaborative web application to create and browse Python notebooks. It lets people create their own notebooks, publish them for others to browse or fork, and work with an AI assistant to write and run Python code.

The application pairs a Vite frontend with a FastAPI backend and uses PostgreSQL for notebook source and chat history. Services keeps the frontend and backend in one deployment, with the frontend served through the CDN.

Here’s how the main parts connect:

  • Editing and running code: When a signed-in user opens their notebook in the editor, FastAPI creates or reuses a Vercel Sandbox running Jupyter, keeping user code isolated from the application backend. The browser connects directly to Jupyter, while mounted Drives provide the Python dependencies and workspace files.

  • Saving and publishing: The browser periodically sends the current notebook to FastAPI. FastAPI saves the source in PostgreSQL, renders changes as HTML, and uploads the result to Blob, so people can read published notebooks through the CDN without starting a Python kernel.

  • Sharing updates: After publishing a change, FastAPI sends a message through Vercel Queues. Each backend instance with connected browsers receives the notification and sends updated notebook listings over WebSockets, so people see changes without reloading.

  • Assisting with code: The agent uses AI SDK for Python and runs inside Vercel Workflows, which saves execution state and retries failed steps. Chat history stays in PostgreSQL, while notebook editing and execution tools work through the connected browser, which sends results back through FastAPI to resume the workflow.

The source code on GitHub includes the complete application and its deployment configuration. You can use it to explore these integrations or as a starting point for your own Python application.

Investing in the Python community

Last December, the Gel Data team, led by me and Elvis Pranskevichus, joined Vercel to build Python support and continue our open-source work.

At the same time, we announced our sponsorship of the Python Software Foundation and committed to funding one year of Serhiy Storchaka’s CPython maintenance through the foundation. Serhiy has authored over 600 commits to CPython’s main branch so far in 2026.

We also sponsored PyCon US and EuroPython this year, where the team and I met Python developers and heard where they were getting stuck. Those conversations help us figure out what to fix next.

We also published PEP 827, which, if accepted, would add type manipulation features that could help frameworks such as FastAPI offer simpler APIs with less boilerplate and more precise type checking.

What’s next for Python on Vercel

We’re continuing to improve Python SDKs, runtime performance, and development workflows for both people and coding agents. If you run into a deployment issue or find something missing in the Python SDKs, share your feedback in Vercel Community so the team can use it to guide that work.

#34842. Introducing Vercel Drives: persistent storage for agents

📅 27 Oct 2026 | Category: other | Source

Agents often handle complex work that continues across runs. As that work evolves, they may need a new environment with different tools, runtimes, or compute. They should be able to continue working with the same files when they change environments.

We built Vercel Drives to keep an agent’s files independent of its execution environment. It is now generally available for Vercel Sandbox. Agents can mount the same drive in a new environment configured for the next task and continue where they left off.

Persisting state with a drive

Create a drive once, then mount it when you create a sandbox. From the CLI:

Or from the Sandbox SDK:

In this example, everything under /workspace persists on the drive. Everything else belongs to the sandbox. The next sandbox that mounts the drive finds the repository, and anything else the agent wrote there, where the previous run left it.

The drive keeps the agent’s files independent of the sandbox running it. An agent can resume work in a new sandbox or switch runtimes without transferring its workspace. Other sandboxes can mount the same drive.

Sharing state across sandboxes

Agents can prepare files on a drive once and reuse them across sandboxes. If one agent builds a dataset on a drive, other agents can mount read-only copies to analyze the data or generate reports without rebuilding the dataset. They use the shared files as input and save their results separately.

Agents can also fork a drive to explore different approaches independently. Each fork starts with the drive’s contents and provides its own writable workspace. Agents can try different transformations of the dataset in parallel without changing the original or affecting one another. Forks don’t merge back into the original drive.

Forking is generally available.

Get started

Vercel Drives is now generally available for Vercel Sandbox on all plans.

Drives default to 1 TiB, or 1 GiB on Hobby, with up to 16 TiB available. See the documentation for configuration, snapshots, and limits, or the changelog for what changed at GA.

AI Gateway Production Index — October 2026

Every month, AI Gateway routes tens of trillions of tokens between production applications and AI labs. That traffic gives us a view of what AI usage actually looks like in today's enterprise, and we publish it here monthly. See the Production Index reports from July, August, and September.

October 2026 summary

  • Open-weight models now process more than seven in ten gateway tokens and account for nearly one in four dollars. Their share of spend has more than quadrupled since June.

  • September’s gateway spend was about 13 times December’s, while the average price per token was 47% lower. Almost one in three teams changed their most-used lab in September, an index record.

  • Nearly 70% of September’s gateway spend on Chinese models went through US-based providers, up from less than 10% in December.

  • Jev was the fastest-adopted model in AI Gateway history, reaching 35% of paid teams in its first two weeks, but it accounted for just 0.27% of gateway spend over that same period. Opus 5.5 took more than one in ten gateway dollars in its own first two weeks, the largest spend share of any September model launch.

Frontier spend up 900%, spend share down 22%

In August, open-weight models processed the majority of AI Gateway token volume for the first time. The money is now following. Open weight’s share of spend has more than quadrupled over the last three months, from one in twenty gateway dollars in June to nearly one in four in September.

Open weight's growth is coming from both ends of its price range, and it mirrors the wider gateway. The cheapest models drive token growth, while the expensive models drive spend.

Led by Kimi K3, models priced at least four times the open-weight average cost per token accounted for about two-thirds of the increase in open-weight spend.

In contrast, DeepSeek-v4.1-Flash alone processed nearly half of all September tokens but took just 2.6% of spend. Its price per token was about a fifth of the open-weight average.

Customers are increasing budgets on both sides of the market. Since December, spend on frontier models has grown tenfold; spend on open-weight models has grown more than seventyfold.

In September, 68% of teams that put more money into open-weight models did the same for closed-weight models. And more than two in five teams already paying for frontier models spent more on them than in August, the highest share this year.

Spending on the frontier is still growing, but spending on alternatives is growing faster. A company can spend more with a frontier lab while relying on it for fewer workloads, so the lab gets more money, but a smaller part of the customer’s business.

AI spend increases 13x while the cost per token halves

Market share is changing hands inside a market that is getting much bigger and cheaper.

September's gateway spend was about 13 times December's, an increase of 1,180%, while the average price per token fell 47%. The median paid customer active in both December and September more than doubled its spend.

Teams are spending more, but labs have to keep winning their business. In September, nearly one in two teams changed their most-used model. And almost one in three changed their most-used lab, an index record.

Even teams with lower token volumes use a wide mix of models. Since December, teams that processed at least 10 million tokens over that period used an average of 15 different models. The average rose to 26 for teams processing at least 100 million tokens, and 42 for those processing at least a billion.

The model is becoming a replaceable part of a much larger investment. Companies can continuously improve their AI products and workflows while changing which models power them. They can spend more on AI without becoming more dependent on any one lab.

Chinese models are big business for American providers

More than two-thirds of September’s gateway spend on Chinese-origin models went to US-based providers, up from less than a tenth in December. The Chinese lab builds the model; the American provider runs it and sells access.

DeepSeek’s models processed 58% of all gateway tokens for 6.6% of spend. More than four in five of those tokens were served by DeepSeek itself, yet two in five dollars spent on its models went through US-based providers.

Moonshot AI, the Beijing-based lab behind Kimi, accounted for 3.6% of gateway tokens and 13.2% of spend in September. US-based providers served nine in ten of those tokens.

Z.ai, also based in Beijing and the creator of GLM, accounted for 7.2% of all tokens and 4.5% of spend. US-based providers served seven in ten.

Customers can use Chinese models through access sold by American providers. For teams that put more money into Chinese models in September, an average of 53% of their spending on those models went through US-based providers and 41% through China-based ones.

The same Chinese model can compete with US-based models while generating revenue for US-based providers.

September model launch scorecard: Jev, Opus 5.5, and GPT-6

Whether a model launch is successful depends on what you measure: how broadly it’s tried, how much usage and spend it receives, or what share of its initial users return. We ranked every model launch in September with at least two weeks of data by these metrics; the tables show the top ten for each. The full scorecard is at the end of the report.

Jev is the most-adopted and most-called model

In its first two weeks, Jev reached more than a third of paid teams, nearly double the reach of Sonnet 5.5 in second place. This is the fastest adoption of any model in AI Gateway history.

Jev also received the most requests of any model in September, even though it launched halfway through the month. Of the teams that tried Jev in week one, 55.6% returned in week two, the fifth-highest retention rate.

Jev is a decision model. Compared with typical language-model requests, a Jev request is faster, cheaper and uses a fraction of the tokens. So although its adoption was fast and broad, it accounted for just 1% of the month’s tokens and 0.15% of spend.

In September, Jev quickly became a popular model for production while remaining a tiny part of the inference bill.

Opus 5.5 takes more than one in ten gateway dollars

The launch that received the most dollars was Opus 5.5, with more than twice the share of any other September launch, followed by GPT-6 Astra and DeepSeek-v4.1-Flash.

Opus 5.5 caught on quickly, with almost nine in ten dollars coming from teams already using Opus 5. Existing customers were trying the new release while the wider Opus family was losing market share.

Across all versions, Opus accounted for almost a third of gateway dollars in September, down from one in two in August. Anthropic’s overall share fell below half of total gateway spend for the first time, dropping from 63.7% to 43.9%.

Luna brought users back; Astra brought spend

GPT-6 Luna reached nearly three out of every twenty paid teams in its first two weeks, in third place behind Jev and Sonnet 5.5. But its return rate was the highest of the month; almost two-thirds of the teams that tried it in its first week came back in the second.

GPT-6 Astra reached a smaller audience but took more budget. In its first two weeks, it accounted for about one in twenty gateway dollars; Luna accounted for less than one in a hundred. Luna reached almost three times as many teams while Astra captured more than five times the share of spend.

OpenAI is attracting more customers with Luna, but capturing far more money with Astra, even though fewer teams use it.

#34834. Vercel and Shopify make agents first-class shoppers

📅 27 Oct 2026 | Category: other | Source

Agents already shop on the web, but they often use pages and tools originally built for people and search engines. Building a better shopping experience for agents means treating them as first-class shoppers, with product information they can read directly and tools designed for agents to shop.

Today, Vercel Shop, our open source Next.js storefront template for Shopify, is generally available. Teams can launch storefronts optimized for how people, search engines, and agents interact with them.

Vercel Shop is built on Shopify’s Hydrogen SDK. The SDK gives teams access to the store’s product catalog, cart and order management, payments, and checkout to build custom storefronts. Earlier this year, Vercel and Shopify announced plans to rebuild Hydrogen to work across JavaScript frameworks. Today, the rebuilt SDK is generally available.

Give agents the information and tools they need

Vercel Shop makes product pages available as machine-readable content, including price, availability, and options. The same product URL can serve a visual page to people or product information that agents can read without interpreting the page’s layout. The template also includes structured data embedded in pages and sitemaps to help search and answer engines discover and understand the products.

Shopify co-developed the Universal Commerce Protocol (UCP), which gives agents a standard way to search a store’s catalog, read product details, check availability, build a cart, and get a checkout link. Vercel Shop makes these capabilities discoverable at the merchant’s own domain, so agents can use MCP to search products and build carts without navigating the site.

Customize the experience for all customers

Vercel Shop brings the store’s product catalog, cart, and checkout together with a Next.js storefront, product information and shopping tools for agents, and a shopping assistant powered by eve. The storefront and assistant live in the same codebase, so teams can customize the store’s design and how the assistant helps shoppers.

Skills included in the template guide coding agents through setup, customization, and template updates. Teams can create an experience where shoppers browse product pages or ask the assistant to find products and add them to their cart. Both share the same cart, so shoppers keep what they’ve added as they move between experiences.

Storefronts built with Shopify and Vercel

Today, we launched our merch store at vercel.store with limited-edition drops. It’s built on Vercel Shop. The store’s shopping agent helps shoppers find products, add them to their cart, and continue to checkout.
